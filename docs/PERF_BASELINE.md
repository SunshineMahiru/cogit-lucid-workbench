# 启动耗时基线

记录日期：2026-11-13。启动数据取自构建 `d4b6069`，内存数据在其后几个提交上复测。设备为 Mate 70 Pro 模拟器，应用为 debug 签名包。

## 方法

冷启动用 `aa force-stop` 杀掉进程，等 4 秒让系统回收，再计时下面这条命令：

```bash
hdc shell aa start -a EntryAbility -b com.sunshinemahiru.cogitlucid -W
```

`-W` 会等到应用进入前台才返回，所以计的是「命令发出」到「首页可交互」的墙钟时间。同一台机器上 `hdc shell echo ok` 往返约 320 ms，是这条链路的固定开销，下表同时给出扣掉它之后的值。

每次启动后立刻 dump 一次布局，确认「记录者」已在树上，说明计时终点不是白屏。

## 结果

| 场景 | 三次实测 | 中位 | 扣除传输开销 |
|---|---|---|---|
| 冷启动（杀进程后） | 1502 / 1785 / 1448 ms | 1502 ms | 约 1.18 s |
| 热启动（退到桌面再回） | 1324 ms | 1324 ms | 约 1.00 s |
| 传输基线（`echo ok`） | 327 / 330 / 312 ms | 327 ms | — |

## 说明与局限

- 冷启动这三次的离散度接近 300 ms，模拟器本身不是稳定计时环境；要看趋势就得在同一台机器、同一时段重复测。
- `-W` 的返回点服从系统调度，不是精确的首帧时刻；这里把它当作上限，真实首帧不会更晚。
- 热启动 1 s 里包含一次首页刷新（前台回来会重算统计），没有拆开。
- 页面切换、列表滚动帧率还没测。

## 内存

读 `hdc shell cat /proc/<pid>/status` 的 `VmRSS`，每次操作后等 2 到 4 秒再读。

| 场景 | VmRSS |
|---|---|
| 冷启动停在首页 | 236 MB |
| 打开数据看板 | 不变 |
| 首次打开关系星图 | 239 MB |

### 页面往返不泄漏

先看现象：按「进页面 → 返回」循环，关系星图十五次从 238.9 涨到 249.8 MB，设置页十次从 244 涨到 252 MB，两组速率都是每往返约 0.8 MB。只看这一段，很像每次进入漏掉一块固定大小的内存。

于是在两个页面的 `aboutToAppear` 与 `aboutToDisappear` 里各加一行日志（验完即拆，未进仓库）。六次进出设置页，日志里 appear 与 disappear 各六条，一一对应——**页面实例正常销毁，没有堆积**。

再连跑二十次，每五次读一次：237 → 236 → 240 → 238 → 242 MB。读数会**下降**，在一段区间里上下浮动，不随次数单调上升。

结论：**没有泄漏。** 应用启动后堆会涨到一个约 240 MB 的工作集，之后在正负几 MB 内波动；前段看到的「每往返 0.8 MB」是工作集还没涨满时的填充过程，不是持续流失。

### 两次误判的教训

第一轮只测星图，看到中段出现 832、844、844、800 这样规律的常数增量，判定「每次固定分配未释放」，并归因到画布。第二轮加设置页做对照，发现设置页涨得一样多，画布被排除。第三轮加生命周期日志与二十次长跑，才发现连「增长」本身都是工作集填充，不是流失。

单点测量加上短样本，足以造出两条看起来很有说服力的错误结论。性能归因至少要三样东西：对照组、实例生命周期证据、足够长的样本。
